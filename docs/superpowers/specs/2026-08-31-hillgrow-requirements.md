# HillGrow — Owner Requirements (verbatim)

**Date:** 2026-08 (brainstorm)  
**Status:** Reference — the system design spec (2026-08-31) is the binding document


HillGrow is a modular automated indoor growing system built around ESP32-DevKitC V4 controllers.
The system consists of one Master Controller and one or more Zone Controllers. All controllers use the same ESP32-DevKitC V4 hardware platform.
The design must be modular, configuration-driven, and expandable. Adding another zone or adding shelves to a zone should require configuration changes, not architectural changes.

### 1. System hierarchy
```
HillGrow
├── Master Controller
│   ├── Wi-Fi / Web UI
│   ├── Global climate control
│   ├── Central ventilation
│   ├── Water reservoir management
│   ├── Global system configuration
│   └── Communication with all zones
├── Zone 1  (Shelf 1..4)
├── Zone 2  (Shelf 1..2)
└── Zone N  (1–4 shelves)
```
A zone is a logical and physical group of shelves controlled by one ESP32-DevKitC V4. Each zone supports 1 to 4 shelves. A shelf is the smallest independently controlled growing unit. Example zones: Tomato, Chili, Herb, Strawberry, Experiment. The firmware must not hard-code crop types; crop names and behavior come from configuration.

### 2. Master Controller
Hardware: ESP32-DevKitC V4. Central coordinator and user-facing controller; the only controller that requires Wi-Fi. Responsibilities: host the local HillGrow web interface; connect to the house Wi-Fi network; store global configuration; maintain the logical mapping between physical Zone Controllers and named zones; communicate with all Zone Controllers; collect telemetry from every zone and shelf; display current state, alarms and history; send high-level commands/setpoints to zones; control global equipment; perform global safety monitoring; handle optional future remote/cloud connectivity. The Master should continue operating locally even if the internet is unavailable. Internet/cloud services must never be required for watering, lighting, ventilation or safety.

Master-controlled equipment (typical): central DUKA TT125 ventilation fan; motorized outside-air intake damper; motorized exhaust-to-workshop damper; motorized exhaust-to-outside damper; window blackout shutter; main water reservoir refill solenoid; reservoir level / weight monitoring; potential global temperature/humidity sensors; potential future heater/dehumidifier. The Master decides global ventilation strategy based on room conditions (e.g. exhausting toward the workshop should eventually consider temperature and dew point / absolute humidity, not simple RH).

### 3. Zone Controller
Every zone uses an ESP32-DevKitC V4. All Zone Controllers should run the same firmware binary. Zone identity is based on the ESP32 factory MAC/eFuse identity. The Master maps that hardware identity to a logical configuration such as: MAC 24:6F:28:xx:xx:xx → Zone ID 3, Name "Herbs", 4 shelves. The Zone Controller is responsible for real-time control of its local shelves. It must remain safe if communication with the Master disappears: local watchdogs, output timeout handling and safe-state logic. The Master sends desired state / configuration / setpoints; the Zone performs the actual hardware control.

### 4. Shelf abstraction
Each Zone supports 1–4 Shelf objects, each an independent configurable unit containing: LED lighting; water pump; circulation fan; two soil moisture sensors; crop configuration; lighting configuration; watering configuration; sensor calibration; runtime state; fault state. Conceptually `struct Shelf { ShelfConfig config; ShelfSensors sensors; ShelfOutputs outputs; ShelfState state; };` Shelf logic should be encapsulated, not spread through the firmware.

### 5. Shelf hardware
Grow lights: 24 V "V24S" LED bars, each with two independently controllable channels: WHITE and RED, PWM controlled. A four-shelf zone therefore needs up to 8 independent PWM outputs. LED power is switched through MOSFET drivers; the ESP32 never powers LEDs directly. **(Decision update, see Part B: PWM is generated by a PCA9685 on I²C, not by ESP32 LEDC.)**

### 6. Soil moisture
Each shelf has 2 × DFRobot SEN0193 capacitive soil moisture sensors (A = left, B = right) to detect uneven moisture. Keep both raw measurements separately; derived values: average, min, max, difference. A large difference can indicate uneven watering or sensor failure. Do not simply average and discard the individual readings. Values must be calibrated per installation / soil type.

### 7. Watering
Each shelf has one dedicated 12 V peristaltic dosing pump, fed from a central atmospheric reservoir (no mains-pressure water at any shelf). The Master fills the reservoir through a separate controlled system. Each Zone operates its local shelf pumps. Only one shelf pump should normally run at a time within a zone/system. Logic: read soil sensors → determine if watering is required → run pump for calculated/configured duration → stop → wait ~10 minutes → read moisture again → evaluate response. Watering must use hysteresis and minimum intervals; never continuously chase the target. Maximum pump runtime and maximum daily watering limits must exist as safety parameters.

### 8. Shelf circulation fan
Small circulation fan per shelf (air circulation, leaf movement, reduce stagnant humid air, support pollination). V1: ON/OFF. PWM speed may be added later.

### 9. Pollination devices
Optional zone-specific outputs, e.g. Tomato Zone: 12 V eccentric vibration motor, short configurable pulses (a few seconds) during daytime. Other zones may not have it. Optional devices are represented through configuration, not crop-specific hard-coded logic.

### 10. Zone I/O expansion
Slow ON/OFF outputs may use a PCF8575 16-bit I²C GPIO expander (shelf pumps, shelf fans, pollination vibrator, future relays/MOSFET outputs). I²C expansion should remain modular.

### 11. Master ↔ Zone communication
Point-to-point UART ring: Master TX → Zone1 RX; Zone1 TX → Zone2 RX; … ; last Zone TX → Master RX. Each node receives a packet and processes it if addressed locally and/or forwards it to the next node. Not a multidrop bus; each link is point-to-point and regenerated by the receiving ESP32. Protocol must include at minimum: source ID, destination ID, message type, sequence number, payload length, payload, CRC, TTL/hop protection. Packets must not circulate indefinitely. Must detect corrupted and duplicate packets. Commands causing physical action should normally be acknowledged, e.g. `SET_LIGHT_LEVEL zone=2 shelf=3 white=70 red=45 command_id=1042` → `ACK command_id=1042 status=OK`.

### 12. Heartbeats and node health
Each Zone periodically reports: node ID, firmware version, uptime, number of configured shelves, sensor states, output states, fault flags, communication statistics. Master tracks online / offline / degraded / fault. If communication is lost, the Zone enters a defined local operating mode instead of stopping plant care; safety-critical outputs still require local timeout protection.

### 13. Configuration model
Separate hardware and crop behavior. Zone hardware: 4 shelves, 8 moisture sensors, 8 LED PWM outputs, 4 pumps, 4 fans. Logical configuration: Zone name = Herbs; Shelf 1: crop = Basil, desired DLI, moisture target, fan schedule; Shelf 2: Tarragon; … Same Zone firmware operates completely different plants; a shelf can change crop without firmware change.

### 14. Expandability
Do not assume fixed zone count, four shelves per zone, or identical shelf equipment. Support 0–N zones, 1–4 shelves per zone, optional actuators, optional sensors, different plant profiles, future sensor types, light types, irrigation strategies. Adding a zone = install ESP32-DevKitC, connect UART ring, power, Master discovers hardware identity, assign configuration, zone begins operating.

### 15. Safety philosophy
Real hardware incl. pumps, fans, lighting and potentially 230 V equipment via drivers/relays. Software defaults toward safe behavior: pump max runtime; limited repeated watering attempts; lighting max duty cycle; invalid sensor readings detected; communication loss does not leave outputs permanently energized; booting/rebooting must not generate unintended output pulses; zone outputs start in defined safe states; watchdogs used; faults latched/logged where appropriate. Commands from web UI or future cloud must never bypass local safety logic.

### 16. Software separation
MASTER FIRMWARE: communication layer, node manager, zone/shelf model, global control logic, water reservoir control, climate control, configuration storage, web/API backend, logging, alarm manager.
ZONE FIRMWARE: communication layer, zone configuration, shelf objects, sensor drivers, output drivers, lighting controller, watering controller, fan controller, optional actuator controller, safety manager, watchdog / health reporting.
Avoid large monolithic loop() implementations. Prefer state machines and non-blocking timing using timers/timestamps. Avoid long delay() calls.

### 17. Core design principle
HillGrow contains Zones; Zone contains Shelves; Shelf contains Sensors + Actuators + Control Configuration. The Master manages the system; the Zone Controller manages hardware and real-time shelf behavior; the Shelf is the reusable production unit. Keep that distinction clear throughout the codebase.

### Additional requirements (owner)
- A **UART command interface on the Master** following the same pattern as `C:\Projects\HillBT\wrover\components\uart_api` (help / set / get commands etc.). It serves as an API and is very useful during test and bring-up.
- The Master has an **embedded web UI** for all control, monitoring, detection etc. The Master creates a Wi-Fi access point; a phone/PC connected to it types **192.168.7.7** and the web UI appears.
- This is a work in progress; expect changes and expansion.
