# coproc — ESP32-C6 co-processor firmware

This is the firmware for the **ESP32-C6 co-processor** soldered onto the
Waveshare ESP32-P4 board that HillGrow's `master` is migrating to. The P4
has no Wi-Fi of its own; the C6 provides it over SDIO via
[`esp_hosted`](https://github.com/espressif/esp-hosted), and `master` talks
to that C6 through `components/cp_ota` (RPC-driven OTA updates) and
`tools/flash_app.py --app cpfw` (staging a new image onto the board).

This project was promoted out of a throwaway spike
(`C:\Projects\hillgrow-p4-spike\eh_cp`) that was scheduled for deletion. Without
this promotion, the P4 master would ship with a co-processor whose firmware
was flashable from a stale binary and rebuildable by nobody.

## What was promoted, and what was dropped

Promoted from the spike, unchanged:
- `CMakeLists.txt`, `main/CMakeLists.txt`, `main/idf_component.yml`, `main/main.c`
- `sdkconfig.defaults`, `sdkconfig.defaults.esp32c6`
- `partitions_eh_cp_ota_4m.csv`
- `dependencies.lock`

Dropped, and why:
- `build/` and `managed_components/` — regenerated by the build; not source.
- The generated `sdkconfig` — regenerated from `sdkconfig.defaults` +
  `sdkconfig.defaults.esp32c6` on first `idf.py -C coproc build`.
- `partitions_eh_cp_ota_2m.csv` — this board's C6 module has 4 MB of flash,
  and `sdkconfig.defaults` selects the 4m table
  (`CONFIG_PARTITION_TABLE_CUSTOM_FILENAME="partitions_eh_cp_ota_4m.csv"`).
  The 2m table was for a different, smaller module and does not apply here.
- `sdkconfig.defaults.esp32`, `.esp32c2`, `.esp32c3`, `.esp32c5`,
  `.esp32c61`, `.esp32s2`, `.esp32s3` — these came along with the upstream
  `esp_hosted` example, which supports many co-processor chips. This
  project targets one specific, soldered-down chip (the C6 on the Waveshare
  P4 board) that will never be swapped for another part, so only the
  `esp32c6` variant is kept.
- The spike's own `README.md` was not copied verbatim; this file replaces
  it with instructions specific to this repo.

**Do not rename the CMake project.** It is deliberately still
`project(eh_cp_wifi_softap)` (see `CMakeLists.txt`), which is what makes the
build output `eh_cp_wifi_softap.bin`. That exact filename is what
`tools/flash_app.py --app cpfw --cp-image` expects you to pass it. Renaming
the project would silently change the artifact name the flashing tool
documents and looks for.

## Building

Target is **esp32c6** (the co-processor chip itself, not the P4 host):

```powershell
& C:\esp\v6.0.1\esp-idf\export.ps1
idf.py -C coproc set-target esp32c6      # first time only; sdkconfig then pins it
idf.py -C coproc build
```

Output: `coproc/build/eh_cp_wifi_softap.bin`.

## Staging the image onto a board

This does not flash an app slot the C6 boots directly (no `idf.py flash`
against the P4's port). Instead, the master stages the raw C6 image into
its own `cp_fw` data partition, and RPC's it across to the co-processor:

```powershell
python tools/flash_app.py --app cpfw --target esp32p4 `
    --cp-image coproc/build/eh_cp_wifi_softap.bin --port COMx
```

`--port` here is the **master's** serial port, not the C6's — the image
goes in over the master's UART/USB, gets wrapped behind a 16-byte `HGFW`
header (magic `HGFW`, length, CRC32, reserved — see
`tools/flash_app.py`'s `HGFW_HDR_LEN`/`HGFW_MAGIC` and
`components/fw_srv/fw_srv.c`'s `FW_HDR_MAGIC`), and is written into the
master's `cp_fw` partition. From there `components/cp_ota` drives the
actual RPC update of the co-processor over the SDIO link.

## CONFIG_EH_TRANSPORT_CP_SDIO_MODE_STREAM=y is mandatory

`sdkconfig.defaults` pins the SDIO datapath to **STREAM** mode, not
upstream's SW_AGGR default:

```
# SDIO datapath mode: STREAM, not the rel-3 default SW_AGGR.
#
# SW_AGGR needs an ESP-IDF carrying commit 4814514 (per-chip descriptor
# limits) to send more than 4092 B per SDIO transfer, and IDF 6.0.1 does not
# have it -- the CP build hard-fails with "this ESP-IDF lacks the send-cap
# fix" and points at `eh.py patch-idf`. We deliberately do NOT patch the
# shared IDF install: it sits outside version control and every other project
# on the machine (including HillGrow master/zone/rescue) builds against it.
CONFIG_EH_TRANSPORT_CP_SDIO_MODE_STREAM=y
```

**Never run `eh.py patch-idf` against the shared IDF install at
`C:\esp\v6.0.1`.** That would modify a toolchain every other HillGrow
project (`master`, `zone`, `rescue`) also builds against. STREAM mode needs
no IDF patch — it uses IDF's own hardware batching — and it is already
proven: the factory C6 negotiates down to it, with the host logging "SDIO
Host operating in STREAMING MODE" at ~1571 kB/s, which is ample for a
246 KB zone image.

## CONFIG_FREERTOS_HZ=1000 is load-bearing, not incidental

Confirmed present in `sdkconfig.defaults`:

```
CONFIG_FREERTOS_HZ=1000
```

The co-processor reboots itself **2000 ticks** after an OTA activate — see
the comment in `components/cp_ota/cp_ota.c` above `CP_OTA_REHANDSHAKE_TIMEOUT_MS`.
At `CONFIG_FREERTOS_HZ=1000` (this project's setting), 2000 ticks is 2
seconds, which comfortably fits inside the 6000 ms re-handshake window
`cp_ota.c` polls for (`CP_OTA_REHANDSHAKE_TIMEOUT_MS`). At ESP-IDF's
**100 Hz default**, 2000 ticks becomes **20 seconds** — well past the
6000 ms window — so a genuinely successful radio update would time out and
be reported as a failure. If this line is ever dropped from
`sdkconfig.defaults` (or overridden lower in `sdkconfig.defaults.esp32c6`),
the co-processor build will silently produce an image that makes every real
OTA look like a failure.

## eh_host_cp_ota_activate() reports ESP_FAIL even on success

On the host side (`components/cp_ota/cp_ota.c`), `eh_host_cp_ota_activate()`
sets the C6's boot partition and the C6 reboots on its own ~2000-tick timer
*inside* the host's RPC wait — so the RPC reply routinely never arrives and
the call returns `ESP_FAIL` even when the activate genuinely succeeded. This
is expected, not a bug: the host code logs it as expected and never trusts
that return code. Instead it polls (bounded by the 6000 ms window above),
re-reads the co-processor's version over the re-established link, and only
confirms the OTA once the new version is actually observed.

## Recovery path

No rollback protection is configured on the co-processor image (no
anti-rollback, no OTA-slot validation beyond the version check in
`cp_ota.c`). If a co-processor image is bad and the board won't come back
over SDIO, the **C6-UART header on the board** is the recovery path — flash
directly over UART to that header rather than trying to RPC a fix in
through a co-processor that may not be answering.

## esp_hosted version pin

`dependencies.lock` pins `espressif/esp_hosted` to **3.0.7** for target
`esp32c6`, built against `idf: 6.0.1`. This is load-bearing: the host side
(`components/cp_ota`) is also built against `esp_hosted` 3.0.7, and it gates
whether it will even attempt an OTA on a **major.minor** version match
between the host's and the co-processor's `esp_hosted` (see `ver_major`/
`ver_minor` and the check in `cp_ota.c`). If this project were rebuilt
without `dependencies.lock` pinning the version, the component manager could
silently pull a newer `esp_hosted`, and the resulting co-processor image
would either be refused outright by the host's version gate, or — worse, if
a future major.minor happened to still pass that gate — could churn against
a host that doesn't actually speak its wire protocol correctly. Do not
delete `dependencies.lock` or regenerate it without a deliberate, tested
decision to move both sides of the version together.

## Not part of the master/zone/rescue regression gate

This project is **not** wired into any build-everything loop alongside
`master`, `zone` and `rescue`. It targets a different chip (`esp32c6`, not
`esp32`/`esp32p4`), has its own `sdkconfig`/`build/` state, and is built
rarely and deliberately — only when the co-processor firmware itself
changes. If you are adding a "build everything" script or CI job, leave
`coproc/` out of it; including it will produce a confusing failure (wrong
target, different toolchain expectations) for no benefit, since nothing
else in the repo depends on it being rebuilt on every change.
